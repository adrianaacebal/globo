# GLOBO food ordering — Practice 1

Authors: Adriana Acebal, María Cuadrado
Resources: **restaurants** (main), dishes, riders, coupons, orders, reviews, complaints, messages

GLOBO is a food-ordering site for restaurant chains in Madrid (Burger King, McDonald's, Sushita,
Telepizza, Honest Greens). Users find a restaurant near them, pick dishes from its menu and place a
delivery or pickup order. Admin pages manage every resource through the REST API.

## Run it

Requires Node 18+. Nothing else.

    npm install
    npm start          -> open http://localhost:3000

`npm run dev` restarts the server on every save (`node --watch`). `npm test` runs the Jest + Supertest
tests in `tests/`. The port can be changed with the `PORT` environment variable.

> **Work in progress (branch `learn-restaurants`)** — the restaurants router is being rebuilt step by
> step. `src/controllers/restaurantsController.js` and `src/validators/restaurantsValidator.js` already
> have all seven operations, but `src/routes/restaurants.js` only wires **`POST /api/restaurants`**
> for now. Until the other six routes are added back, `GET`/`PUT`/`PATCH`/`DELETE /api/restaurants…`
> return the JSON 404, the pages that list restaurants (`restaurants.html`, `search.html`,
> `order.html`) show an error, and 14 of the 74 tests fail (`tests/restaurants.test.js` and the
> restaurants block of `tests/newResources.test.js`). This README describes the API as it will be
> once the router is finished.

## Resources

Every resource has its own router (`src/routes/`), controller (`src/controllers/`) and validator
(`src/validators/`). Controllers only talk to `src/data/store.js` (in-memory store + seed data in
`src/data/seed.js`). For every resource: the `id` is generated by the server and ignored if sent,
unknown fields are stripped, and text is trimmed. Values from fixed lists are accepted in any case
and without accents (`chamberi` → `Chamberí`) and stored with their official spelling.

The resources live in memory, so every restart goes back to the seed data. Only users are saved to
disk (`data/users.json`), so accounts and their order history survive a restart.

### restaurants (main resource)

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| name | string | required, 2–60 characters |
| brand | closed set | `burgerking` \| `mcdonalds` \| `sushita` \| `telepizza` \| `honestgreens` |
| area | closed set | `Centro` \| `Chamartín` \| `Chamberí` \| `Fuencarral` \| `Moncloa` \| `Retiro` \| `Tetuán` |
| type | closed set | `burger` \| `pizza` \| `sushi` \| `vegan` |
| delivery | boolean | `true` (home delivery) or `false` (pickup only) |
| lat | number | required, −90 to 90 |
| lon | number | required, −180 to 180 |

### dishes

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| name | string | required, 2–60 characters; unique per brand (409 if repeated) |
| brand | closed set | same brands as restaurants |
| category | closed set | `main` \| `side` \| `drink` \| `dessert` |
| price | number | 0.1 to 500, rounded to cents |

### riders

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| name | string | required, 2–60 characters |
| vehicle | closed set | `bike` \| `motorbike` \| `car` |
| area | closed set | same areas as restaurants |
| available | boolean | `true` or `false` |
| rating | number | 0 to 5 |

### coupons

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| code | string | required, 3–20 characters, stored in upper case; unique (409 if repeated) |
| percent | number | whole number, 1 to 90 |
| active | boolean | `true` or `false` |
| orderType | closed set | `all` \| `delivery` \| `pickup` |

An active coupon can be typed in the discount box of `order.html`.

### orders

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| customer | string | required, 2–60 characters |
| restaurantId | number | whole number; the restaurant must exist |
| riderId | number \| null | optional; the rider must exist; a pickup order cannot have one |
| type | closed set | `delivery` \| `pickup` |
| status | closed set | `pending` \| `preparing` \| `on-the-way` \| `delivered` \| `cancelled` |
| total | number | 0 to 1000, rounded to cents |
| paid | boolean | `true` or `false` |

Orders confirmed on `order.html` are also stored here with status `pending`.

### reviews

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| restaurantId | number | whole number; the restaurant must exist |
| author | string | required, 2–40 characters |
| rating | number | whole number, 1 to 5 |
| comment | string | required, 3–300 characters |
| verified | boolean | `true` or `false` |

### complaints

Sent from `complaint.html` ("Report a problem") and managed in `complaints.html`.

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| name | string | required, 2–60 characters |
| email | string | required, valid email, stored in lower case |
| brand | string | one of `burgerking`, `mcdonalds`, `sushita`, `telepizza`, `honestgreens` |
| type | string | one of `delivery`, `food`, `payment`, `other` |
| date | string | `YYYY-MM-DD`, cannot be in the future |
| message | string | required, 10–1000 characters |
| status | string | `open`, `in progress` or `resolved`; `open` if not sent |
| createdAt | string | set by the server, kept on PUT |

### messages

Sent from `contact.html` and managed in `messages.html`.

| Field | Type | Rules |
|---|---|---|
| id | number | server-generated, ignored if sent |
| name | string | required, 2–60 characters |
| email | string | required, valid email, stored in lower case |
| subject | string | one of `order`, `restaurant`, `account`, `other` |
| message | string | required, 10–1000 characters |
| status | string | `new`, `read` or `answered`; `new` if not sent |
| createdAt | string | set by the server, kept on PUT |

## Endpoints

The same seven endpoints exist for every resource: replace `<resource>` with `restaurants`, `dishes`,
`riders`, `coupons`, `orders`, `reviews`, `complaints` or `messages`.

| Method | Path | Query params | Success | Errors |
|---|---|---|---|---|
| GET | /api/restaurants | search, brand, area, type, delivery | 200 | 400 |
| GET | /api/restaurants/stats | same filters | 200 | 400 |
| GET | /api/dishes | search, brand, category, minPrice, maxPrice | 200 | 400 |
| GET | /api/riders | search, vehicle, area, available | 200 | 400 |
| GET | /api/coupons | search, active, orderType | 200 | 400 |
| GET | /api/orders | search, type, status, paid | 200 | 400 |
| GET | /api/reviews | search, restaurantId, rating, verified | 200 | 400 |
| GET | /api/complaints | search, brand, type, status | 200 | 400 |
| GET | /api/messages | search, subject, status | 200 | 400 |
| GET | /api/&lt;resource&gt;/stats | same filters as the list | 200 | 400 |
| GET | /api/&lt;resource&gt;/:id | | 200 | 400 (id not a positive integer), 404 |
| POST | /api/&lt;resource&gt; | | 201 + `Location` | 400, 409 (dishes, coupons) |
| PUT | /api/&lt;resource&gt;/:id | | 200 | 400, 404, 409 (dishes, coupons) |
| PATCH | /api/&lt;resource&gt;/:id | | 200 | 400, 404, 409 (dishes, coupons) |
| DELETE | /api/&lt;resource&gt;/:id | | 204 (no body) | 400, 404 |
| GET | /api/health | | 200 `{ "status": "ok" }` | |

Filters combine (`?type=pizza&delivery=true`). `search` is case-insensitive and ignores accents. It
looks in: `name` (restaurants, dishes, riders), `code` (coupons), `customer` (orders), `author` +
`comment` (reviews), `name` + `email` + `message` (complaints, messages). On dishes, `minPrice`
greater than `maxPrice` is a 400.

Error bodies:

- **400 validation** (body, query or id): `{ "errors": [ { "field": "name", "message": "name is required" } ] }`,
  every problem at once. `PATCH` with no known field → `{ "field": "body", "message": "Send at least one of: ..." }`.
- **400 relation**: an order whose `restaurantId`/`riderId` does not exist, a pickup order with a rider,
  or a review of a restaurant that does not exist (same `errors` array).
- **400 bad JSON**: `{ "error": "Invalid JSON in request body" }`.
- **404**: `{ "error": "Dish not found" }` for an unknown id; `{ "error": "Route GET /x not found" }`
  for an unknown route.
- **409**: `{ "errors": [ { "field": "name", "message": "This brand already has a dish with that name" } ] }`
  or `{ "field": "code", "message": "A coupon with that code already exists" }`.
- **500**: `{ "error": "Internal server error" }` (never a stack trace).

## Web order flow (login, menu, order)

These routes are not a resource: they are what `login.html`, `order.html` and the menu pages use.
They live in `src/routes/checkout.js` (outside `/api`). Logging in returns a `token`; the browser
keeps it and `apiRequest` sends it as `Authorization: Bearer <token>`. Routes marked 🔒 answer
`401 { "error": "You need to log in to order", "needLogin": true }` without a valid token.
Sessions are kept in memory, so after a restart users have to log in again.

| Method | Path | What it does | Success | Errors |
|---|---|---|---|---|
| POST | /login | `{ name, email, password }`. Unknown email → registers the user and gives a one-time welcome code `GLOBO-XXXXXX` (10 %). Known email → checks name and password. | 201 (new) / 200 | 400 (name, email, password ≥ 6 chars), 401 |
| GET | /menu?restaurant=Telepizza | Full menu (dishes) of the brand | 200 | 400 (missing), 404 |
| POST | /order 🔒 | `{ restaurant, location, type }`: checks the brand has a restaurant in that area | 201 | 400 (lists the available areas), 404 |
| POST | /order/total | `{ restaurant, items: [{ dish, quantity }], type, travelMinutes, discountCode }`: price breakdown, saves nothing | 200 | 400, 404 (unknown dish) |
| POST | /orders 🔒 | Same body + `password`, `location`, `payment`: confirms the order | 201 | 400, 401 (wrong password), 404 |
| GET | /orders 🔒 | Order history of the logged-in user, newest first | 200 | 401 |

Price rules (`src/pricing.js`, `checkoutController.js`):

- `subtotal` = sum of dish price × quantity (prices come from `/api/dishes`, never from the browser).
- Delivery fee: 5 % of the subtotal if the trip takes 15 minutes or less, 7 % if longer; 0 for pickup.
- Discount on subtotal + delivery fee: an **active coupon** from `/api/coupons` valid for that order
  type (can be reused), or the user's own **welcome code** (10 %, only once).
- `total` = subtotal + delivery fee − discount, rounded to cents.

A confirmed order is saved in the user's history (`data/users.json`) and also created in
`/api/orders` with status `pending`, `riderId: null` and `paid: true` only when paying by card, so it
can be managed from `orders.html`.

## Postman

1. In Postman: **Import** → choose `postman/globo.postman_collection.json` (Collection v2.1).
2. Start a fresh server with `npm start`.
3. Open the collection → **Run** → run all folders in order.

The collection variable `baseUrl` is `http://localhost:3000/api`, so every request reads
`{{baseUrl}}/<resource>`; `siteUrl` (`http://localhost:3000`) is used for the login and order flow.
It has 11 folders: `0. Health`, one CRUD folder per resource (`1. Restaurants` … `8. Messages`),
`9. Login and orders` and `10. Errors` (unknown route, bad JSON, and `GET /src/app.js` returning 404
to show the server code cannot be downloaded). Each CRUD folder creates an item first and saves its
id in a variable (`restaurantId`, `riderId`…), then gets, replaces and deletes it. It also includes
invalid POSTs showing the 400 error array, the filters and every `/stats`. Every request has tests
(`pm.test`).

`postman/collections/Globo API/` (plus `postman/globals/` and `.postman/`) is the same API saved in
Postman's newer folder format by the Postman app. It is a shorter copy: folders 0–7 only (no
messages, no login/order flow, no errors folder) and complaints without PUT/PATCH/DELETE. Use the
`.json` file for the full run.

## Design decisions

- **Invalid query parameters are rejected with 400**, with the same `{ errors: [ { field, message } ] }`
  shape as the body. Ignoring them would return the full list and the user would think the filter
  worked. Unknown query parameters are ignored, because they cannot be wrong.
- **`express.static` is mounted after the `/api` routers and before the JSON 404 and the error
  handler**, and only serves `public/`. API paths are matched first, so a file can never hide an
  endpoint; unknown routes still reach the JSON 404; and the server code (`src/`) and data (`data/`)
  cannot be downloaded.
- **Searching and filtering happen on the server**: the browser only downloads the matching items,
  the rules (case and accent-insensitive search, valid values) live in one place, and `/stats` uses
  exactly the same filters. A database could later do the filtering without touching the pages.
- Orders, reviews and coupons check their relations in the controller (the restaurant or rider must
  exist, coupon codes are unique), because validators only look at the body, not at the data.
